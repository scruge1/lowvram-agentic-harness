# Idea intake and work release

Treat a user's stream of ideas as project input. Capture useful ideas without
automatically turning each topic into an active job.

1. Capture the intended outcome and its source. Label uncertain assumptions.
2. Route it to the existing project authority and queue. Merge duplicates and
   link related work. If ownership is unknown, keep it unassigned in the current
   forward plan rather than creating another global board.
3. Refine it into a short item: outcome, relevant components, prerequisites,
   smallest useful next step, and evidence that would show completion. Include
   resource demand when it affects scheduling.
4. Prioritise against existing commitments. Release work when authority,
   prerequisites, owner capacity, and required resources are available.
5. Verify the actual result and record useful lessons in the owning project.

A new topic alone does not cancel the active objective. An explicit stop or
switch does. An explicit execution request can advance ready work without an
extra confirmation loop; ordinary urgent repairs continue within their scope.

Queued work is not dispatched work. A board state or model recommendation cannot
grant permission, reserve a GPU, or establish completion. Use existing host
checks and resource owners. Independent ready tasks can proceed in parallel
within their actual capacity limits while another task waits.

At checkpoints, distinguish active, queued, and held work. State the dependency
that holds an item and revisit it when that dependency or priority changes.

This is a portable operating procedure. It does not install a scheduler or
enforce work-in-progress limits. Target adoption needs evidence from that
target's normal intake and execution path.
