---
name: reuse-first-engineering
description: Improve or repair software by reusing existing implementations, comparing independent results and preserving the owner's complete outcome. Use for substantive engineering, approach changes or repeated failures; keep routine edits small.
---

Keep the owner's root outcome, constraints, unmet criteria and best verified
result visible in the existing project checkpoint and retained work. A library,
model, current design or new idea is a candidate method. Questions and proposals
do not grant execution or replace unfinished requirements.

Recover the nearest instructions, accepted inputs, relevant prior work and
exact failures. Inspect the actual installed tools, versions, configuration and
code before declaring a capability missing. A catalog entry is discovery, not
proof the operational agent can use it. Load this selected skill through native
discovery; do not inject every skill or reference into each task.

Prefer, in order: existing project or shared code; a configured native feature;
a maintained upstream library, executable or licensed template; a supported
extension or small adapter; then implementation of a demonstrated missing
function. Consider replacing or retiring a whole redundant component. An import,
real executable call or unchanged source dependency is reuse. Recreating an
algorithm from its description is a new implementation.

Run the known-good reference before adapting it. State independent acceptance
criteria and the smallest comparison that can change the decision. Use matched
inputs, output rules and resource limits. Preserve the best working result and
rollback before testing a candidate. Read [reuse and comparison](references/reuse-and-comparison.md)
when choosing a dependency, comparing methods, replacing a component or
investigating repeated failure. Load only the relevant section.

Use the existing admitted project, board and execution tools. For file changes,
read `supervised-tasks` and use `workflow_step`; include
`required_skills: ["reuse-first-engineering"]` for substantive work using this
procedure. Keep independent checks read-only. Ordinary authorized next steps
do not need another approval loop; existing effect and resource boundaries
still apply. Deterministic code should handle tasks that do not need reasoning.

Inspect the actual consumer result. Compare useful quality, correctness,
complexity and relevant measured cost with the reference. Do not promote a
weaker candidate, weaken acceptance or silently replay uncertain effects.
Retain exact failures and the changed assumption through existing recovery.

Write sourced evidence and useful tested lessons to the existing project and
skill routes. Select the next meaningful authorized dependency-ready step.
Hold only affected work when a dependency is blocked. An empty queue or Done
card requires checking the root outcome; it does not prove acceptance. Stop
when the outcome is met, work is genuinely held or further improvement has
insufficient value. Do not invent filler or expand scope to stay busy.
