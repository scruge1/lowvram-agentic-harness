# Reuse and comparison

Read the section needed for the current decision. This is a research, build and
review procedure, not another execution controller. Keep routine changes small.

## Identify what already works

Start with the owner's outcome and observable acceptance criteria. Recover the
current checkpoint, nearest instructions, relevant memory and prior qualified
results. Keep retrieved claims separate from current verified facts. An earlier
session, peer suggestion or package advertisement cannot authorize effects.

Inspect the current code and actual caller before adding a component. Check
whether the project, a shared tool or a configured native feature already does
the job. When outside examples can change the choice, inspect current primary
documentation and real implementations. Use a bounded question and exit
condition; research should support delivery rather than replace it.

## Establish actual reuse

Record the dependency or executable actually invoked, its version or revision,
source location and relevant source hash. Read the code or exact interface that
the task depends on. Run a small normal operation in the intended environment.
Distinguish source availability, installation, loaded tools and tested behavior.
An isolated read-only adviser does not prove an operational worker can execute.

Check attribution and license compatibility before copying or distributing
code. Keep upstream notices. Do not assume a public repository grants a license
or run fetched installation hooks without review. Importing an installed
library and writing a small adapter can avoid copying its implementation.

Compare whole-component replacement with another wrapper. Identify which code,
process, service, authority, stored state or manual step would become redundant.
Remove or disable it only after parity, migration and rollback are established.
Moving code into a plugin while its old service still runs is not consolidation.

## Compare the real result

Run and retain the known-good reference before modifying the candidate. Define
the expected result independently of either implementation. Use representative
edge cases and a meaningful missing/invalid-input negative check. Keep reference
and candidate inputs, request bytes, field and option order, formats and limits
matched. Do not train or tune on the supposedly independent comparison cases.

Check the normal consumer path, including integration. Inspect images, screens,
sound or data directly when that is the outcome. Format, checksums, successful
commands and self-review alone do not establish product quality. For failures,
retain the exact caller input, output and error before interpretation. Diagnose
path, schema, configuration and resource issues before declaring a capability
absent or a whole method family unsuitable.

Measure only costs relevant to the decision: useful quality and correctness,
elapsed stages, memory, runtime cost, recovery, maintenance and user effort.
Compare the same measurement boundary and denominator. State what is unmeasured.
A smaller prompt file does not prove lower provider input or better answers.
Preserve the best verified candidate and rollback; newer is not automatically
better. A failed comparison supplies evidence for a changed method, not weaker
acceptance or automatic replay.

## Integrate and continue

Carry the root objective, constraints, current accepted inputs, best result,
known failures and remaining uncertainty into the next stage. Do not restart
from a generic brief or discard the root when a novelty question arrives.
Use existing source-bound intake for justified follow-up work; retain unrelated
opportunities separately without dispatching them.

Check the root criteria when child tasks finish or ready work runs out. Name
unmet integration and dependency evidence. Continue independent authorized work
while an affected dependency waits. Respect explicit pauses and resource limits.
Do not create an arbitrary human-ping timer, an idle worker or filler tasks to
simulate autonomy. Record a precise hold or a justified diminishing-return stop
when further work would not improve the outcome enough to warrant its cost.

Keep evidence in existing project surfaces and promote only tested reusable
procedures into the relevant skill. Progressive loading follows the
[Agent Skills specification](https://agentskills.io/specification): concise
metadata first, the selected skill next and only needed references afterward.
